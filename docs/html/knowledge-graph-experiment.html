One profile, two intros — decomposed, not just embedded

Adrian's profile and his two real Boardy intros — one he accepted, one he declined — were each sent to Gemini 3.1 Flash Lite with one instruction: pull out a small knowledge graph (person → works_in → industry → has_subcategory → …), the way relationship-recommendation research represents a profile as entities and typed edges instead of a single vector. The three graphs below are merged into one: people never link to each other directly — only through concept nodes they each happen to touch. A second, dashed layer of type nodes — Industry, Location, Need, and so on — sits above that: each one is not from any single profile, it's the taxonomic parent of every concept node sharing that type, the "Industry has_subcategory Subcategory" shape carried one level higher.

“Proptech” is the only node touching all three people

Everyone in this trio ends up at a Proptech node — but by very different routes, and it doesn't predict the outcome. Adrian reaches it in two hops through his own company; Danny and Kunle both reach it in three, through Real Estate — a second bridge node that connects the accepted and declined candidate to each other, without ever connecting either of them straight to Adrian.

Shared topic, opposite outcome

This is a single illustrative pair, not a claim about the dataset — but it's a clean picture of this project's actual finding: both intros are anchored in the same industry concept, so topical relevance alone doesn't separate the accepted intro from the declined one. What differs is downstream of it — Danny's needs (Capital, Peer Network, Mentoring) sit closer to Adrian's own asks (Seed Funding, Operator Peers) than Kunle's do (Deal Flow, Partnerships) — visible here only as separate, unconnected need nodes off each root.

Node type was assigned per-graph by the model independently — Proptech surfaced as an industry for Adrian and Kunle but a subcategory for Danny. Merged here by label text only, which is itself worth noting as a limitation.

Extraction: one google/gemini-3.1-flash-lite call per profile via OpenRouter (temperature 0.2, ≤14 nodes / ≤16 edges each), prompted directly in the style of entity+typed-edge social-graph decomposition. Source pairs: the real accepted pair (cm5x8qsuy… → cmoini4d9…) and real declined pair (cmoini4d9… → cmdghuwkl…) from this repo's seed dataset. Graphs merged by case-insensitive label match, not embedding similarity — a cheap, illustrative decomposition from a single LLM call each, not a validated ontology or a claim generalized beyond this one trio.
