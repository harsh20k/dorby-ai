Explode the ask, then route on it

Our proposal said the mixture of experts should read the lookingFor section by section. What we actually built collapses all of it into a single integer. This is the plan to close that gap — and an honest account of what it can and cannot buy us.

01 — the gapWhat we proposed vs. what runs today

Two pipelines were built. They were never connected to each other.

The section machinery exists and works: it embeds each of a seeker's asks, scores candidates against them, and combines the results. We used it to settle which combine rule is best. But its output is a report, not a feature. It never reaches the model.

Meanwhile the mixture of experts reads a hand-built table of 12 numbers. Exactly one of them knows sections exist — n_sections, which counts them. Two profiles of roughly 7,000 characters each, and every ask the person wrote out, arrive at the model as the number 13.

Why this matters

Whatever the model can possibly learn is bounded by what survives that funnel. When plain logistic regression matches the mixture of experts — as it has three times now — that is evidence the architecture is unnecessary and evidence the bottleneck might be upstream of it.

02 — the ground truthThree numbers that shaped the design

Measured on the 200 real pairs before writing any of this.

2,302 (pair, section) rows from 200 pairs — a 12× multiplier on training rows
5 median sections per seeker, with a tail out to 116 — so we cap at 8
994 distinct section headings; the top 8 cover just 8.5% of them

That last number kills the obvious version of this idea. You cannot write "one expert for hiring, one for fundraising, one for customers" — people phrase their asks 994 different ways and no small set of buckets covers them. Section headings must be embedded and routed on, never enumerated. The specialisation has to be discovered, not assigned.

There is also a subtlety worth naming: we get one outcome per pair, but many sections per pair. We know the intro was accepted; we do not know which ask it satisfied. In the literature this is multiple-instance learning — the bag has a label, the instances do not. The pooling step is where that gets resolved, which is why it carries so much weight below.

03 — the architectureOne row per ask, not one row per pair

The unit of prediction changes. That single move is what makes everything else possible.

The input, precisely

BlockDimsWhat it is
Section ↔ candidate similarity3cosine, rank percentile, cosine − keyword overlap

Pair-level scalars12the current feature table, repeated per section
Into each expert47
Gate input (separate path)16projected section embedding, and nothing else

Each expert, and why it grows

Today an "expert" is a single Linear(12→4) followed by a ReLU. That is not a network — it is a weighted sum with a kink. Four of them mixed together can barely express more than one logistic regression, which is a plain reason the mixture never beat one.

The proposal is 4 experts, 2 layers each: 47 → 24 → ReLU → 24 → 16 → ReLU. About 1,700 parameters per expert, ~7,000 in total. That is affordable now for a reason that did not hold before — we are fitting 2,302 rows, not 111, and can pre-train on roughly 30,000 synthetic section rows first.

05 — attentionWhy it belongs here, and only here

The strongest version of the idea is also the one we already have evidence for.

We tested five ways of combining section scores into a pair score. The winner was a temperature-sharpened softmax — a rule that mostly listens to the best-matching ask, but not only to it. Interestingly, pushing it all the way to "just take the maximum" was worse. Some blending helps.

Here is the observation that makes attention the obvious next step: that softmax is attention with the weights frozen. Same shape, same maths — we simply picked the weights by hand instead of learning them. Learned attention is the natural generalisation of the thing we already measured as best, and it costs about fifty parameters and one head.

06 — alternativesWhat else we could do instead

Ranked by what the evidence and the latency budget actually allow.

OptionCallReasoning
Per-section experts + learned attention pooling Recommended Generalises the pooling rule we already measured as best, gets 12× more training rows, and makes routing mean something we can check.
Keep the fixed softmax pooling Control arm Run it beside the above. If attention does not beat it, we learn that pooling was never the bottleneck — a cheap and genuinely useful negative result.
Self-attention between a seeker's own asks Not yet Lets asks modulate each other ("they want a hire and funding"). Plausible, but we have no evidence such interaction exists, and it costs parameters we cannot spare.
Cross-attention over raw text No That is a cross-encoder. It reads both profiles together at query time, which is dead on arrival under a 100 ms budget, and needs orders of magnitude more labels than 200 pairs.
Set Transformer / DeepSets Overkill Heavy machinery for permutation-invariant sets. At a median of five sections, single-head attention already covers it.
The risk worth stating up front

Attention pooling and the expert gate are both mechanisms for "decide what matters for this input." They may quietly do the same job twice. The ablation that settles it is cheap: mixture-of-experts + attention, against a plain single network + attention. If those two land in the same place, the mixture was never the useful part — which is, honestly, what the last three experiments have each been hinting.

07 — order of workHow we would build it

New isolated package moe_sectioned/ — own config, own artifacts directory, nothing in the earlier experiments touched.

  1. Put both populations in one embedding space Encode ~300 real profiles with Qwen3-Embedding-8B, which the synthetic batch already uses. Today the two sides use different models, which is exactly why the embedding channel had to be thrown away last time.
  2. Explode into section rows Split each seeker's asks, cap at 8, embed each one. 2,302 real rows, ~30,000 synthetic.
  3. Pre-train on synthetic, within-seeker Ranking one candidate above another for the same seeker was worth +0.131 last time — the single largest effect we have measured. Keep it.
  4. Fine-tune on real pairs, cross-validated by seeker Never let one person appear in both training and validation.
  5. Read the diagnostics before the score Expert usage, routing decisiveness, and whether routing is secretly tracking who is asking rather than what they asked. That last one has caught us before.
  6. One shot at the 69-pair holdout — and only if earned The bar to clear first is 0.6398, plain logistic regression. Nothing has beaten it yet. If the cross-validated result does not clear it, we do not spend the holdout.

Latency is unaffected, which is worth saying plainly: the asks belong to the seeker, candidates stay embedded offline in batch, and query time is about five short encodes plus a vector lookup. Nothing here moves us toward the per-candidate model calls that the budget rules out.

08 — what would make this failStated before we run it

  • The asks may not be the signal. Production already filtered these pairs for topical relevance. Every pair here passed that bar, so the residual question — will these two actually connect — may live in tone, timing, or effort, none of which sections capture.
  • The label is per-pair, the rows are per-section. If pooling cannot resolve which ask mattered, the extra rows are 12× more noise rather than 12× more signal.
  • Synthetic pre-training has failed once already. Every model trained on the synthetic batch scored below the no-model floor. The teacher labelling that data is only right about 58% of the time on real pairs, and better features do not raise a ceiling set by label quality.
  • Four experts on 2,302 rows is still small data. Fold-to-fold variation in past runs was ±0.15 AUC. Any improvement smaller than that is not a result, it is weather.
The bar

Logistic regression on roughly 105 real pairs scores 0.6398. Keyword cosine with no training at all scores 0.5660. Both are still unbeaten by anything we have built. This plan is worth running because it tests a specific idea we have never actually tested — not because the architecture has earned confidence.
