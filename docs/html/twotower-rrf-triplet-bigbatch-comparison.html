A bigger batch closed the retrieval gap — by trading away classification accuracy

Follow-up to the first triplet fine-tune. This run only changed how many rivals the model saw per training step (bigger batch, 2 negatives instead of 1). Recall@1 caught up to Boardy's production model. Pair accuracy fell below it. Here's the three-way comparison and what to try next.

What changed, in one line

Only the training crowd size changed — real batch size 2→6, negatives per training row 1→2. Same synthetic training data, same loss function, same holdout. That one change moved recall@1 from 0.276 to 0.345 (tied with production) — and moved pair AUC down from 0.610 to 0.576.

02

Why one metric went up while the other went down

Recall@1 — closed the gap

Recall@1 asks: out of the whole candidate pool, does the true match come out ranked #1? Practicing against more rivals per step (bigger batch, 2 negatives) is a closer rehearsal for that exact test — so it improved, right up to production's own level.

Pair AUC — got worse

Pair AUC asks a narrower question: given just one candidate, is it good or bad? Spreading attention across more rivals each step means less repetition on any single head-to-head comparison — the narrow judgment call got noisier, not sharper.

Same trade-off already seen in the first report, now confirmed by pushing the same lever further in one direction: retrieval and pairwise classification are pulling on different things. Whichever matters more depends on the product — one best pick shown to a user favors pair AUC; a ranked shortlist favors recall@1/MRR.

03

A real ceiling, not a design choice

The batch size wasn't picked freely — it was found by testing on the GPU directly. Batch size 8 used 64 of 79 GB; batch size 10 ran out of memory immediately. Training used batch size 6 (a safety margin below that wall), a real 3x increase over the original run's batch size of 2, but well short of the 32-64 originally hoped for. The bottleneck is long profile text (up to ~1,700 tokens) with no memory-saving trick available for this specific model.

04

Next steps

  1. Separate the two changes. This run moved batch size and negatives-per-row together. Run each alone to find out which one is actually doing the work.
  2. Try a blended target. Instead of optimizing purely for "beat every rival" or purely for "beat one rival," score checkpoints on a mix of both — aiming to land between this run and the original, not at either extreme.
  3. Get denser negative coverage. Only half of the training seekers had two genuinely different rejected candidates to compare against; the rest had to reuse the same one twice. A larger labeled batch with more rejections per seeker would let this experiment use 3+ negatives instead of 2.
  4. Rerun clean. A checkpoint-selection bug was found and fixed after this run finished — it happened to pick the right epoch anyway, but a fresh run now benefits from the fix by default.
