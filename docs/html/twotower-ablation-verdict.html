Dorby AI · two-tower ablation · combined verdict

Bigger batches helped. The extra negative hurt.

The previous run moved two levers at once and couldn't say which one mattered. Running the missing corners of a 2×2 grid — twice each, so there's a real noise floor to measure against — gives a clear answer, and reverses one of the assumptions behind the original experiment.

Effect 1 — micro-batch

Positive in every comparison, and the retrieval gains clear the noise floor. Raising micro-batch from 2 to 6 is worth roughly +0.05 MRR and +0.06 recall@1. This is the mechanism the earlier experiment guessed at: more candidates competing inside a single training step is closer rehearsal for ranking against a real candidate pool.

Effect 2 — the second negative

Negative in all four comparisons, with pair-AUC drops that clear the noise floor. The cause looks like a data limitation rather than a flaw in the idea: only 189 of 385 seeker-queries actually have two different rejected candidates, so 27.5% of second-negative slots are duplicates of the first. A repeated negative teaches nothing new but doubles that one example's pull on the loss.

A correction worth stating plainly

Arm A's first run scored recall@1 0.4138, which looked like a clean sweep over the production model on every metric. The replicate came in at 0.3793. Averaged, Arm A is level with Voyage-4-large on pair AUC and MRR (both gaps sit inside the noise floor) with a modest recall@1 edge of about 1.5 queries. It is the best configuration this project has trained, and it beats the previous bigbatch attempt outright — but "beats production on everything" was the single-run reading, and it did not survive being run again. That is precisely why the second replicate was worth the ten minutes.

04

A side finding: the dev set can't pick winners

Arms A and C initially shipped their final epoch by accident — a checkpoint-retention setting had deleted the earlier epochs before best-epoch selection ran. Fixing it produced a surprise: the correctly selected model scored worse on the real holdout than the accidental one (Arm A: 0.5983 vs 0.6112 pair AUC).

The 60-row dev set only spans 0.50–0.58 across all five epochs — a narrower range than its own run-to-run wobble. It cannot reliably rank checkpoints, so "best epoch" is close to a coin flip right now. Both numbers are reported and averaged above rather than keeping the flattering one.

05

What to do next

  1. Push micro-batch higher. It's the lever that works and 6 wasn't the ceiling — the measured out-of-memory limit was 8 at k=2, and k=1 costs less memory, so 8–10 should fit. Cheapest remaining gain.
  2. Re-test extra negatives without the duplicates. Restrict to the 189 seeker-queries that genuinely have two distinct rejections. Smaller dataset, but it would answer whether real extra negatives help — which this ablation could not, because half of them were copies.
  3. Fix the dev set before trusting checkpoint selection again. Either enlarge it, or select on a retrieval-shaped metric instead of triplet accuracy, so selection optimizes for the thing that's actually improving.
  4. Replicate the bigbatch corner. It's the one cell in the grid with a single run and therefore no error estimate.
