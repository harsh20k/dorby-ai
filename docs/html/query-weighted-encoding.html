The profile is drowning the ask

The search query is 2% of the seeker's text. Encoding it separately and weighting it up takes recall@1 from 0.18 to 0.30 — with no training at all.

Every model in this project builds the seeker side as one string: eight tagged profile fields with Search query: … appended. Measured on the 200 real pairs, that query averages 218 characters against a 10,178-character seeker string.

profile — 8 biography fields
profile · 9,960 chars · ~2,450 tokens search query · 218 chars · 2.1%

That 2% is the only part that says what the person wants right now. The rest is biography. So: encode the two separately and combine them as normalize(α·Q̂ + (1−α)·P̂), sweeping α from all-profile to all-query.

The α curve

MRR recall@1 dotted = today's concatenated baseline · all 200 real pairs

Both metrics rise monotonically as the query gains weight, cross the current baseline by α≈0.2–0.3, and plateau around α≈0.6–0.7. α=0 is profile-only; α=1 is query-only.

alpha_0.6 beats today's baseline on every metric on every population — all-200, train-131 and holdout-69. On the holdout, recall@1 goes from 8 of 29 to 17 of 29.

concat_baseline reproduces frozen Voyage-4-nano's published all-200 row digit-for-digit (0.5593 / 0.3171 / 0.1800 / 0.5900), so the harness is doing nothing new to the baseline.

Why it works

Jaccard token overlap with the true candidate versus a random distractor:

Seeker textvs targetvs distractorDiscrimination
query only0.03140.02441.29×
profile only0.16970.16301.04×

The profile overlaps everything about equally. 1.04× is almost no discrimination — it isn't neutral filler, it's noise, and averaging it into the seeker vector dilutes the query's 1.29× edge. Text-level tricks (front-loading, repeating) help only a little because concatenation still forces one shared vector; separating the encodes is what actually works.

The caveat, stated first

The retrieval metric is partly circular

“Retrieval” here means finding the candidate who was actually introduced to this seeker — and those candidates were originally selected by Boardy production, using this same search query. A query-only encoder is therefore partly re-deriving production's own retrieval decision. Some of that recall@10 of 0.9100 is exactly that.

Two things bound it. Name leakage is ruled out: only 6 of 100 queries share a rare capitalised token with their target, and they are topic terms (Vancouver, SEIS, PayPal), not identity giveaways. And the accept/decline metrics are not circular at all — pair AUC and hard-negative AUC score one pair directly, with no corpus and no ranking. There, query_only's hard-negative AUC of 0.5914 is the best of any model measured on all 200, ahead of Qwen micro-6 (0.5608) and Arm A (0.5558).

Treat the retrieval numbers as an upper bound and the hard-negative AUC as the clean signal. Both point the same way.

It's cheaper to serve, not more expensive

seeker_vector = normalize( α · encode(query) + (1−α) · encode(profile) )

encode(profile) depends only on the user's profile, so it is precomputed offline and cached exactly like candidate vectors. The only online work is encode(query) — ~55 tokens instead of ~2,500. That is a materially faster online encode than today's path, plus one vector add and a normalize. No fine-tuning, no new model, no new serving dependency.

Caveats

  • One run, no replicate. The effect is far larger than the one-query resolution limit (R@1 moves 12 of 100; 9 of 29 on the holdout), but the exact α optimum is not resolved — 0.6 vs 0.7 is 5 queries.
  • Text-level arms confound “more weight” with “protected from truncation” at 4096 tokens. The α arms don't, which is why they carry the conclusion.
  • Frozen Voyage-4-nano only — untested on the fine-tuned adapters, Voyage-4-large, or the open-weight models.
  • The easy/hard negative split is pinned to the baseline text for every arm, so arms are scored on identical populations.
  • The 100 positive queries come from only 78 unique seekers.
