# Why Voyage-4-nano ≈ Voyage-4-large on this eval

**Question:** Why do local `voyage-4-nano` and API `voyage-4-large` look so similar offline on the intro-matching dataset?

**Headline metrics** (`artifacts/*/metrics.json`, 100/100 hard pairs, ~178 corpus):

| Model | AUC | MRR | Top-1 | R@10 | Cosine gap (pos−neg) |
|-------|-----|-----|-------|------|----------------------|
| nano (local, dim 1024) | 0.561 | 0.301 | 0.16 | 0.60 | 0.0098 |
| large (API, dim 1024) | 0.573 | 0.310 | 0.13 | 0.70 | 0.0103 |

---

## Main reasons (ranked)

### 1. Shared Voyage-4 embedding space (by design)

Voyage’s Voyage-4 announcement and the nano model card state that **all Voyage-4 models produce compatible embeddings** in one shared space, so nano / lite / base / large can be mixed for query vs document.

- Blog: [The Voyage 4 model family: shared embedding space with MoE architecture](https://blog.voyageai.com/2026/01/15/voyage-4) — “All four models produce compatible embeddings… embeddings generated from different models can be used interchangeably.”
- HF: [`voyageai/voyage-4-nano`](https://huggingface.co/voyageai/voyage-4-nano) — “Embeddings generated by different Voyage 4 models (`voyage-4-large`, …, `voyage-4-nano`) can be directly compared and used interchangeably.”

Nano is the open-weight cousin for local/prototype; large is the MoE production model in that same space—not a different retrieval objective.

### 2. Identical eval setup collapses model differences further

Both baselines use:

- Same text builders (`baselines.bert_frozen.text`: field-tagged seeker / candidate)
- Same asymmetric roles (`encode_query` / `input_type=query` vs document)
- Same Matryoshka dim **1024**
- Same pair AUC + retrieval protocol

So we are comparing two members of one family under matched inputs, not two independent stack designs.

### 3. Hard-negative ceiling: both hit the same “topical similarity” wall

Discrimination is semantic; lexical overlap is similar across classes. Pair cosine gaps are tiny for **both** (~0.01). Most positives are not Top-1 for either model (**81/100** queries miss Top-1 for both). The label set rewards fine intro-worthiness that generic topical embeddings do not encode; capacity differences between nano and large barely move that margin.

### 4. Context-length gap (8192 vs 32k) barely applies here

Nano was run with `max_length=8192` (of 32k); large supports 32k via API. On this packed text, HF `voyage-4-nano` tokenizer lengths over **351 unique** strings:

| | mean | p50 | p90 | p99 | max | >8192 |
|--|------|-----|-----|-----|-----|-------|
| tokens | 1970 | 1568 | 3195 | 8480 | 10610 | **5 (1.4%)** |

Almost all dossiers fit under nano’s truncate; the 32k headroom of large is not the reason for the small metric gap.

### 5. Small-n noise on headline deltas (especially Top-1)

n = 100 retrieval queries. Top-1 **0.16 vs 0.13** is **3 queries**; McNemar on discordant Top-1 (nano-only 6, large-only 3) has binomial p ≈ **0.51** — not distinguishable from noise. Large’s edge on R@5 / R@10 / median rank is more consistent than the Top-1 flip.

## Quantitative evidence (cached embeddings, no new API calls)

Recomputed from `artifacts/voyage_nano/emb_*.npy` and `artifacts/voyage_large/emb/*.npy` with the same text builders:

| Evidence | Result |
|----------|--------|
| Pair-score Pearson (200 labeled pairs) | **0.88** (Spearman 0.87) |
| Same-text embedding cosine (nano↔large, pos seekers / cands) | **~0.94** mean |
| Target-rank Spearman | **0.85**; median \|Δrank\| = **2** |
| Top-1: both correct / both wrong / agree | 10 / **81** / **91%** agreement |
| R@10 agreement | **86%** (both hit 58; large-only +12, nano-only +2) |
| Mean Jaccard of top-10 lists | **0.55** |
| Cosine gaps | nano 0.0098, large 0.0103 |

Interpretation: scores and rankings track closely; large is a bit better at pulling the true match into the top-10, but both fail the same hard cases.

## Implications

**Nano is enough for iteration when:**

- You are debugging text packing, metrics, or training loops
- You need free local encode (no API key / spend)
- Relative A/B of features matters more than absolute Boardy parity

**Large still matters when:**

- You need the Boardy-faithful production reference
- You care about ranking depth (R@5/R@10, mean/median rank) on a larger or easier corpus
- You plan asymmetric serving (large docs, smaller query model) as Voyage recommends
- You want the MoE quality ceiling before claiming beat-Boardy offline

---

## What would make them diverge

1. **Different text packing** — full dossiers vs curated fields; nano truncate starts to bite if packing grows past ~8k tokens often.
2. **More / easier retrieval data** — larger corpus or less hard negatives; shared-space cousins separate more on RTEB-style benchmarks than on this 100-query hard set.
3. **Rerank or multi-stage** — a cross-encoder / LLM stage on top of either bi-encoder will dominate the nano–large gap.
4. **Fine-tune / two-tower on intro labels** — task adaptation can move both; if you fine-tune only one side of the family, compatibility and scores diverge.
5. **Dim / precision mismatch** — e.g. nano at 2048 vs large at 256, or int8 vs float32, without matching protocol.

---

## Bottom line

Similar offline numbers are expected: **same embedding space + same inputs + tiny label margin + almost no truncation disadvantage + n=100 noise**. Use nano to iterate; keep large as the production yardstick—and expect real lift from better labels/packing/rerank/fine-tune, not from switching nano→large alone on this set.
