# Objective & what the data actually means

This is the canonical statement of the project's goal and of what the 200 real
labeled pairs represent. Other docs should link here rather than restating it.

## What the 200 real pairs are

All 200 pairs are **introductions Boardy's production system already surfaced**
— production looked at the seeker's profile + `searchQuery`, decided the
candidate was a good intro, and recommended it. Every pair in both files
therefore passed production's own relevance bar.

The label is the **real-world human outcome** of that recommendation:

| File | Records | Meaning |
| --- | --- | --- |
| `data/dataset_positive.json` | 100 | Production suggested it **and the humans accepted** — marked it a good match and actually connected. |
| `data/dataset_negative.json` | 100 | Production suggested it **and the humans declined** — did not move forward. |

There is no `label` field; membership in the file *is* the label (see
[`data/dataset_summary.md`](../data/dataset_summary.md)).

## The objective

Learn from the training portion of that data to **predict the accept/decline
outcome on the frozen holdout portion**. Being right on the holdout is the
final objective of the project — everything else (frozen baselines, synthetic
data generation, the two-tower LoRA fine-tune) exists to serve that one number.

The split is user-disjoint and frozen in
`data/synthetic/seed_split.json`: **131 real train pairs / 69 real holdout
pairs** (`eval_pair_ids`) — roughly the intended 70/30, with the exact ratio
set by the constraint that no user may appear on both sides. Load it via
`twotower/data.py::build_split_bundle()`; never sample seeds, few-shots, or
training pairs from the holdout side.

## Why this framing changes how to read every result

**1. The negatives are production's false positives, not random mismatches.**
A real negative is a pair that was topically plausible enough for production to
recommend it, and *still* got declined. So the negative class is hard by
construction — there is no easy-negative population in the real data at all.
This is the correct lens for:

- Modest absolute AUCs across the board (~0.58–0.64). Separating accepted from
  declined *among already-plausible intros* is a much harder problem than
  separating relevant from irrelevant candidates, and the numbers should be
  read against that harder problem.
- `dataset_summary.md`'s observation that lexical query↔match overlap is
  near-identical across the two classes (~0.19 mean). That is exactly what this
  framing predicts: both classes are topically on-target, so keyword overlap
  cannot be the discriminator.
- The hard-negative slice metrics hovering near chance
  ([`possible-bugs.md`](possible-bugs.md) #4,
  [`twotower-run-001-results.md`](twotower-run-001-results.md)).

**2. We are not modeling topical relevance — production already does that.**
The signal we need is the residual: *given that this intro looks right on
paper, will the two people actually connect?* That residual lives in fit,
timing, stage, seniority, reciprocity of interest, and preference/logistics
constraints — not in whether the two profiles are about the same subject
matter. This is why plain TF-IDF keyword cosine gets ~0.59 and then stalls
(`possible-bugs.md` #3): lexical overlap is measuring the thing production
already solved, not the thing we are asked to predict.

**3. It sets a distribution bar for synthetic data.** Synthetic negatives are
currently generated by violating one axis of matching semantics on purpose
(`wrong_side`, `wrong_stage`, `wrong_role`, `geo_mismatch`, `prefs_conflict` —
see `synth_pipeline/prompts/generate_neg.md`). Those are *constructed*
mismatches. A real negative is a plausible intro a human declined. Those two
populations are not the same thing, and a model trained to recognize the former
is not necessarily learning the latter.

This is a distinct concern from the confirmed prompt-artifact leakage bug
(`possible-bugs.md` #4) and is **an implication of the framing, not a measured
finding** — no experiment has yet isolated how much of the synthetic-data
transfer gap is attributable to it. Worth designing an experiment for before
the Arm C regeneration is scaled up; the pairing-based approach in
[`profile-generation-local-and-bedrock.md`](profile-generation-local-and-bedrock.md)
inherits the same question, since a fusion-scorer label is also a constructed
judgment rather than an observed human decision.

## Hard constraint: <100 ms end-to-end latency

Accuracy on the holdout is necessary but not sufficient — the winning approach
must also **serve a query and return retrieved candidates in well under 100 ms**.
This is a serving-time budget on the online path, and it rules out whole classes
of approach regardless of how well they score offline:

**Ruled out at serving time:**

- **Any per-candidate LLM call** — an LLM judge or generative reranker in the
  online path. Not close to feasible; these are hundreds of ms to seconds each.
- **Cross-encoders that must run per (seeker, candidate) pair.** Even a small
  cross-encoder over a meaningful candidate set blows the budget, because cost
  scales with candidates scored rather than being amortized.
- **Realistically, remote embedding API calls for the candidate side** —
  including `voyage-4-large`, Boardy's production model, whose API round trip
  alone is likely to consume most or all of the budget. It remains the accuracy
  *reference point*; it is not automatically a viable *serving* configuration
  under this budget.

**Why the two-tower shape is the right bet under this constraint.** A two-tower
/ bi-encoder factorizes the score so the candidate side never has to run online:

1. Encode all candidate profiles **offline**, in batch, and store the vectors.
2. At query time, encode **only** the seeker + `searchQuery` — one forward pass.
3. Retrieve by approximate nearest neighbour over the precomputed vectors.

So the online cost is one query encode plus one ANN lookup, and it stays flat as
the candidate pool grows. This is the main architectural reason to prefer the
two-tower over a cross-encoder here, independent of accuracy — and it is worth
stating explicitly because the accuracy-vs-latency tradeoff usually favours
cross-encoders on accuracy alone.

**Implications for the current candidates:**

- **TF-IDF** is trivially fast (sparse dot products) and is the cheapest thing
  that gets ~0.59 — a real contender on the latency axis even though it plateaus
  on accuracy.
- **Voyage-4-nano** run **locally** is the plausible online encoder: small
  (340M), open-weight, and only ever needed for the query side at serving time.
  Whether one local nano query-encode fits the budget on target hardware is the
  question that decides the whole design.
- **The TF-IDF + nano fusion** (current best, AUC 0.6397) needs both encoders on
  the query side. Still bi-encoder-shaped and still amortizable, but its budget
  is the sum of the two.
- **The LoRA fine-tune adds no serving cost over base nano** — adapters can be
  merged into the base weights, so a successful fine-tune is "free" latency-wise
  relative to frozen nano. That makes it the most attractive way to buy accuracy
  under this constraint.

**Status: unmeasured.** No latency benchmark exists in this repo yet — every
number here is a metrics/accuracy number, and the budget has not been tested
against any configuration. Standing up an end-to-end query-latency benchmark
(query encode + ANN retrieve, p50/p95, on representative hardware) is a
prerequisite for calling any approach a win, and should not wait for the
accuracy work to finish.

## What a win looks like

Beating the best frozen baseline on the matched 69-pair holdout
([`baseline-results-holdout.md`](baseline-results-holdout.md)) — currently the
TF-IDF + Voyage-nano fusion at pair AUC 0.6397 / hard-neg 0.6034, with
Voyage-4-large (Boardy's production embedding model) at 0.609/0.602 — **while
serving a query in <100 ms.** Both conditions, not either one. Per the decision
gate in [`two-tower-fine-tune-plan.md`](two-tower-fine-tune-plan.md), the
holdout is evaluated **once**, at the end, not repeatedly while iterating.
